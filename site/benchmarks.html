How a run counts

The harness sits outside both engines

bench/harness/bench.py reads progress, CPU, and memory from the container cgroup. The engine's own metrics are never the score.

Same budget

CPUs 4–7 and 4,608 MiB for each engine. Flink runs JobManager and TaskManager in that one cgroup, parallelism 4. The broker and the harness sit on other cores.

Throughput is the steady slope

A preloaded backlog is drained from the start. The rate is a line fit through commit jumps between 20% and 95% of the backlog, after the first commit.

Every row is checked

The expected table is recomputed from the generator formula. A run with a missing row, an extra row, a wrong value, or a duplicate version is dropped.

Latency is the clock

Producers stamp event_time with wall time. For Paimon, latency is the snapshot that makes the row visible. For a Kinesis sink, it is the moment the tail reads the record back.

Reading the tables

What stays inside the comparison

Two machines, labeled

Redpanda numbers are the Apple M5 median. Kinesis, SQS, and NEWS2 numbers are one Linux box with 24 CPUs. They are not one ranking. NEWS2 is the 4 October pair in bench/results/2026-10-04.jsonl.

floCi is in the path

Kinesis and SQS are the floCi emulator on localhost:4566. SQS rates, and the ~80K rows/s Kinesis sink, describe that emulator. A preloaded Kinesis drain reads data already in the stream: ten of twelve runs reached 903K–1.05M rows/s, and two stayed at 186K and 321K. On AWS the engine reads shards in parallel.

Sinks are at-least-once

Kinesis and SQS have no transaction that ties the output to the input offsets. These runs still verified a clean output. A crash can republish; consumers dedupe on source_version.

Raw files

Every figure on this page comes from bench/results/*.jsonl. Which runs sit in each median is bench/README.md. python3 bench/report.py prints medians over every verified run in those files, including older builds.
