Use case · NEWS2 · Linux · 4 Oct 2026

Split each vital. Score it. Union the minute.

A clinical early-warning pipeline, laid out the way the thesis does it on Paimon. Six measurement tables, six NEWS2 score tables, then one wide row per patient per minute. Tachyon and Flink 2.2.1 ran that graph on the same input, inside the same 4 CPU and 4.6 GiB cap.

The whole pipeline

Thirteen Paimon tables, no topic in between

Redpanda only feeds the first layer. Each measurement type is stored, scored with its own NEWS2 bands, and kept. The window reads the six score tables and writes news2_wide.

Watermark

Event time is measurement_timestamp. The watermark lags it by 10 seconds. The window is a one-minute tumble.

A missing vital

Some patient-minutes omit oxygen saturation. The wide row is still written: that value is empty and that score is 0.

What each layer holds

Five measurement tables and five score tables hold 500,250 rows. Oxygen holds 493,672. The wide table holds the 500,000 closed windows, and nothing else.

No hop in the middle

The score tables are the input of the window. A topic does not stand in for any of the thirteen Paimon tables.

Same layers, two runtimes

How each engine runs that graph

The tables, the NEWS2 bands, the window, and the wide-row columns match. The processes do not have to.

Flink 2.2.1 · Paimon 1.4.2

One job, four slots

JobManager and TaskManager share the cgroup. All thirteen statements run as one statement set, so the stages share those four slots. Each Paimon table has four buckets. The window is a UNION ALL of the six score tables, then TUMBLE.

  • Parallelism 4, inside CPUs 4–7
  • Commit every 1 second, exactly-once checkpoints
  • TaskManager stays 3,072 MiB. Managed memory is 128 MiB, so the task heap is 2,190 MiB and each sink can spill a 32 MiB buffer
Tachyon

Thirteen pipelines, one cgroup

Each stage is one process and one Paimon output: six splits, six scores, one window. The window process reads the six score tables directly. There is no JobManager and no network shuffle. Tables have one bucket.

  • Same CPUs 4–7 and the same 4,608 MiB cap
  • Commit every 1 second, with the Paimon snapshot
  • Throughput is the wide table. CPU and memory are the whole container

Why a run counts

The wide rows match the input, not the other engine

Independent expected rows

The checker reads the topic and folds it. Each wide row must have the right patient, window, six values, and six NEWS2 scores. news2_score must be the sum. (patient_id, window_start) must be unique.

All thirteen tables

Each measurement table and each score table may contain only its type. Score rows must match that type’s bands. A duplicate primary key drops the run.

Short Tachyon slope

Three snapshot jumps in under a second still meet the harness rule of at least three points between 20% and 95%. Flink’s slope is the longer series. Both are the same formula.

The size both finished

250 × 2,000 is the backlog both engines completed inside the cap. A 500 × 5,000 backlog filled Flink’s task heap before the wide table was done. The cap stayed 4,608 MiB.

NEWS2 bands are the thesis scoring job: respiratory rate, oxygen saturation, systolic pressure, heart rate, temperature, and consciousness (1 scores 0, anything else scores 3). The other measured workloads are on the benchmarks page.
