Philosophy

A different way to think about streaming

Flink is a platform you run pipelines on. Tachyon is a pipeline that runs itself. Six principles drive every design decision:

  1. 01

    SQL is the product

    All transformation logic is SQL — DataFusion plus a small set of streaming extensions (watermarks, TUMBLE / HOP / SESSION, state TTL). I/O and deployment live in one YAML. There is no pipeline code to write, review, or maintain.

  2. 02

    A pipeline is a self-contained unit

    One binary, one process, no coordination layer. The moment a cluster becomes the unit of deployment, operating the platform becomes a second product you have to run.

  3. 03

    Scale by key, not by cluster

    One key K partitions Redpanda, the state, the merge, and the Paimon buckets. More volume means more partitions and more independent instances with disjoint keys — no cross-node shuffle, no rebalancing coordinator.

  4. 04

    Opinionated by design

    One state backend (redb), one checkpoint mechanism, one writer per bucket. The configuration surface is the essential: connectors, inputs, output, key, partitions. Everything else has a default we stand behind.

  5. 05

    Inherit the hard parts

    A vectorized SQL engine is a multi-year project. DataFusion gives us the planner and Arrow execution; Paimon gives us the lakehouse table; Redpanda gives us the broker. We build only the streaming semantics: watermarks, state, windows, exactly-once.

  6. 06

    The output is a table

    Every pipeline writes to Paimon — a streaming-first lakehouse table (LSM, changelog, CDC, ACID). The result of a pipeline is data you can query from any engine, not a topic you have to subscribe to.

Deploy & operate

From cluster to container

What it takes to run, scale, and recover a pipeline — side by side.

The Flink way

  1. Provision a cluster: JobManager + N TaskManagers (JVM)
  2. Tune the memory model: heap, managed memory, network buffers
  3. Stand up coordination: ZooKeeper or Kubernetes
  4. Pick a state backend — RocksDB or heap — and tune it
  5. Plan savepoints before every deploy
  6. Scale by rebalancing tasks and migrating state
  7. Debug across three kinds of JVM logs

The Tachyon way

  1. Write pipeline.sql — the logic
  2. Write pipeline.yaml — inputs, output, key, partitions
  3. Run: tachyon run pipeline.sql pipeline.yaml — one container
  4. Watch one HTTP endpoint: throughput, lag, p99, state size
  5. Scale by adding an instance — the consumer group rebalances, buckets stay disjoint
  6. Recover by restoring the last local checkpoint — no cross-node barrier
  7. Change the logic by editing the SQL and redeploying the binary

The why

Why we built it this way

Every constraint is a choice. These are the ones that shaped Tachyon — and the trade-offs we accepted.

01

No Flink runtime

We considered Running pipelines on Flink and inheriting its coordination, state, and checkpointing layers.

We chose A lean Rust process per pipeline. We build watermarks, state, and checkpointing ourselves — and a pipeline fits in one process: no JVM, no cluster, no coordinator.

02

DataFusion instead of our own engine

We considered Writing a vectorized SQL engine from scratch — a multi-year effort with a well-trodden road ahead of it.

We chose DataFusion: the planner, optimizers, and vectorized Arrow execution already exist. Our engineering goes into the layer that actually differentiates: streaming semantics.

03

Paimon as the output

We considered Iceberg, Delta, and Hudi — the established lakehouse tables.

We chose Paimon: it is streaming-first (LSM tree, changelog, CDC, ACID) and has a native Rust writer. The same table serves streaming and batch — one output for both worlds.

04

Redpanda as the broker

We considered Kafka, Pulsar, NATS — each with its own partitioning and operations story.

We chose Redpanda: Kafka-compatible, C++ thread-per-core, Jepsen-verified. Low latency with a small footprint — and the key that partitions the broker is the same key that partitions the state.

05

redb as the only state backend

We considered RocksDB (Flink's default, C bindings), SQLite (relational, not a KV), LMDB (fast, but C), and tiered memory→disk approaches.

We chose redb: pure Rust, single-file, copy-on-write. A checkpoint becomes a file snapshot — with reflink, near-instant. One backend, one mechanism, zero choices to get wrong.

06

One key, one writer per bucket

We considered Independent partitioning per layer — each subsystem with its own key and its own routing.

We chose A single aligned key: Redpanda partition key == state key == merge key == Paimon bucket key. Colocated state, no write conflicts, scaling in lockstep — validated at compile time.

07

No distributed runtime

We considered A Flink-style distributed runtime: tasks spread across nodes, coordinated by a JobManager, with cross-node shuffles and barriers.

We chose Self-contained instances. Coordination is where operational complexity lives, so we removed it: inputs are co-partitioned by key, fan-in is a local merge, and checkpoints are local barriers. The trade-off we accept: if an upstream stream isn't partitioned by K, one repartitioning stage fixes it — a known, declarable cost instead of a hidden one.

Use cases

What people build with it

Tachyon turns streaming data into a lakehouse, without the operational overhead.

NEWS2 early warning, split by vital

Six measurement tables, six NEWS2 score tables, then a one-minute window in Paimon. The same graph on Flink 2.2.1, same 4 CPUs and 4.6 GiB. Tachyon committed the 500,000-row wide table at 260–275K rows/s against 10–11K, on about one core instead of 3.85.

Real-time analytics on event streams

Ingest JSON events from Redpanda, transform with SQL (filter, join, aggregate), and write a continuously-updated Paimon table. Windowed aggregations close automatically via watermarks.

INSERT INTO orders_lake
SELECT window_start, window_end,
       order_id, COUNT(*) AS events
FROM TABLE(
  TUMBLE(TABLE orders,
         DESCRIPTOR(event_time),
         INTERVAL '1' MINUTE)
) GROUP BY window_start, window_end, order_id;

Cross-service event unification

Multiple services publish events with different schemas. Tachyon's schema converter normalizes them to a common base before the SQL layer — no code, just config.

inputs:
  - name: web_orders
    topic: orders-web
    convert_to: combined_orders
  - name: app_orders
    topic: orders-app
    convert_to: combined_orders

CDC pipelines to the lakehouse

Ingest change-data-capture events (insert, update, delete) and maintain a primary-key table in Paimon. Sequence numbers resolve out-of-order updates; rowkind fields encode the operation type.

output:
  table: warehouse.dbo.customer_events
  key: customer_id
  bucket: 8
  sequence.field: source_version
  rowkind.field: op

Session windows across services

Combine multiple service streams with UNION ALL, apply a session window on the unified stream. One query replaces what used to require a whole Flink job graph.

INSERT INTO user_sessions
SELECT service, session_start, session_end,
       COUNT(*) AS hits
FROM TABLE(
  SESSION(TABLE combined_streams,
          DESCRIPTOR(event_time),
          INTERVAL '30' MINUTE)
) GROUP BY service, session_start, session_end;
